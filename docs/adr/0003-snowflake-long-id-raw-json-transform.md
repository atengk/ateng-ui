# 0003. 基于 Axios 原始转换管道的雪花 Long ID 大数防截断方案

## 状态

Accepted (已接受)

## 背景与决策上下文

后端分布式架构普遍使用 64 位整型（Snowflake ID，长达 19 位）作为全局实体主键。由于 JavaScript 双精度浮点数（IEEE 754）的最大安全整数为 $2^{53}-1$（9007199254740991，16 位），经由原生 `JSON.parse` 反序列化会导致末位截断失真，在详情查询、修改与删除回传时引发致命数据串号。

调研评估了三种解决路线：

- 路线 A：在 Axios 响应拦截器中补救。不可行，进入拦截器时已被 Axios 默认反序列化并发生精度截断。
- 路线 B：引入第三方 `json-bigint` 全量替换解析器。虽然安全，但解析耗时增加 5~10 倍，在大数据量报表和分页查询下严重卡顿，且生成的 BigInt 对象无法被原生 `JSON.stringify` 再次序列化，极易诱发下游崩溃。
- 路线 C：重写 Axios `transformResponse`，在原始文本阶段使用纳秒级正则匹配将 16 位以上无引号数字加双引号，再交付 V8 原生 C++ `JSON.parse`。

## 架构决策

1. 确立“Axios `transformResponse` 原始正则加引号 + 原生 `JSON.parse`”为全链路唯一受控的雪花 ID 防失真方案；
2. 匹配规则严格限定为：针对 `[:\s\[,]` 边界后跟 16 位及以上长数字，加双引号转为纯 JavaScript 字符串；
3. 严格遵循 AGENTS.md“原生优先与零臃肿依赖”防线，坚决不引入 `json-bigint` 等重型第三方库。

## 效果与权衡

- **收益**：100% 保障 64 位雪花 ID 精度完整，产物为原生 `string`，保持 V8 极致反序列化性能，零外部依赖。
- **代价**：对于极特殊的长数字字符串字段（已带引号），正则通过前置边界与无引号特征严格排除，需在单测中维护完备的对抗性测试用例。
